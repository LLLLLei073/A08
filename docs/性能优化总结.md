# A08 数智党校学习系统 — 性能优化总结

> 适用范围：A08 项目（Vue 3 + Vite 5 单体仓库，含 admin / mobile / server 三包，NestJS 托管静态资源）。
> 本文档汇总截至 2026-07-25 已落地的全部性能优化项，含改动位置、实测数据与验证结论。

---

## 一、背景与目标

- **问题**：admin / mobile 首屏加载慢，最严重时首屏耗时超过 1 分钟，影响评委体验与日常使用。
- **目标**：
  1. 降低首屏 JS / CSS 体积，减少不必要的首屏请求；
  2. 降低服务端重复计算与公网带宽；
  3. 在不牺牲安全性的前提下，让重复访问“几乎瞬时”。

## 三、核心改动详解

### A1 — md-editor 动态加载（首屏减负最大项）

- **文件**
  - `packages/admin/src/views/content/ContentView.vue`
  - `packages/mobile/src/views/content/ContentView.vue`
- **改动**：将 `MdEditor` / `MdPreview` 由顶层静态 `import` 改为 `defineAsyncComponent(() => import('md-editor-v3'))`；并顺带动态加载 `highlight.js`、`atom-one-dark` 样式、`screenfull`。仅在「文章正文」对话框 / 视图挂载时才拉取编辑器运行时。
- **安全**：通过 `md-editor-v3` 的 `config({ markdownItConfig(md){ md.set({ html: false }) } })` 关闭 HTML 渲染，防存储型 XSS。
- **实测效果**
  - admin 列表页 chunk：351 KB(gz) → 4.8 KB(gz)
  - mobile 列表页 chunk：129 KB(gz) → 2.7 KB(gz)
  - `index.html` 首屏 preload 仅剩 `index-*.js`(34 KB gz) + vue + axios + CSS；约 296 KB 的 md-editor 运行时 chunk 已退出首屏预加载列表。

### A2 — 构建期预压缩直发（零运行时 CPU）

- **新增 `scripts/precompress.cjs`**：遍历 `public/admin`、`public/mobile`，对 `.js/.css/.html/.json/.svg/.wasm/.map` 生成 `.gz`(gzipSync l9) 与 `.br`(brotliCompressSync q11) 兄弟文件；跳过已压缩、空、>8MB 文件。零第三方依赖（Node 内置 `zlib`）。
- **新增 `packages/server/src/common/middleware/precompress.middleware.ts`**：在静态服务与运行时压缩中间件**之前**运行；客户端支持 br/gzip 且磁盘存在对应兄弟文件时，以流方式直发预压缩文件并结束响应（零运行时压缩 CPU）。哈希资源标记 `immutable`，其余 `no-cache`；`/api`、`/uploads` 路径显式跳过。
- **实测效果**
  - 生成 335 个 `.gz`/`.br` 文件，约节省 4616 KB；
  - `/admin/` 走 br（245 字节，`no-cache`）；静态资产 `vue-*.js` 走 br（`public, max-age=31536000, immutable`）。

### A3 — 服务端只读接口缓存（白名单 + Redis）

- **新增 `packages/server/src/common/interceptors/http-cache.interceptor.ts`**：注册在 `TransformInterceptor` 之后（最内层），拿到控制器原始返回值。
- **安全策略（防跨用户数据泄漏）**
  - **白名单（共享、非用户相关只读接口）参与 `public` 缓存：**
    - `/api/statistics/overview`（60s）
    - `/api/statistics/by-org`（60s）
    - `/api/statistics/trend`（60s）
    - `/api/orgs/tree`（300s）
    - `/api/contents/categories`（300s）
    - `/api/questions/categories`（300s）
  - **其余 GET（含 `/auth/me`、`/users`、`/tasks/my` 等用户相关接口）：`private, no-cache`**，绝不进入共享缓存；
  - **非 GET 写操作：`no-store`**。
- **降级**：Redis 不可用时（`RedisService.isReady()` 为 false）仅设置 `Cache-Control`，不读写缓存，与 RedisService 整体降级策略一致。
- **一致性**：命中时返回 `of(缓存对象)`，外层 `TransformInterceptor` 仍包成 `{ code, message, data }`，线上报文与未命中完全一致。
- **验证结论（curl 真值，已通过）**
  - 白名单 #1 MISS：`Cache-Control: public, max-age=60`，无 `X-Cache`
  - 白名单 #2 HIT：`Cache-Control: public, max-age=60` + `X-Cache: HIT`
  - 非白名单 GET：`Cache-Control: private, no-cache`
  - POST：`Cache-Control: no-store`

### P0~P1 / #2~#7（已落地，摘要）

- 服务端 gzip/brotli 压缩 + 哈希资源长缓存；md-editor 移出首屏入口；
- admin：echarts 按需引入 + keep-alive 路由缓存 + element-plus 按路由分包；
- #2 路由空闲预加载、#3 Pinia TTL 缓存、#4 图片懒加载、#6 OSS+CDN、#7 brotli 压缩；
- #5 字体子集化：中文界面无西文字体可裁切，收益极低，评估为 **跳过（N/A）**。

### B1 — mobile Vant 样式按需（去除 233KB 全量 CSS）

- **文件**：`packages/mobile/src/main.ts`
- **改动**：删除 `import 'vant/lib/index.css'`（Vant 全量样式，构建后 233 KB / brotli 47 KB）。声明式组件（`<van-button>` 等）的样式由 `vite.config.ts` 中的 `VantResolver` 在编译期**按需注入**；仅手动引入被函数式 API 用到的命令式组件样式：
  ```ts
  import 'vant/es/toast/style';   // showToast
  import 'vant/es/dialog/style';  // showConfirmDialog
  ```
  （代码全局仅使用 `showToast` 与 `showConfirmDialog` 两个命令式组件，见 `grep` 核对结果。）
- **安全**：无样式丢失风险——构建产物中 408 个 `.van-*` 类样式完整保留在首屏 `index-*.css`（含被用到的组件样式 + 业务样式），非白屏。
- **实测效果**
  - 旧首屏 CSS：独立 `vant-*.css` 233 KB(raw) / 47 KB(br)；
  - 新首屏 CSS：单一 `index-*.css`（Vant 按需 + 业务）72 KB(raw) / **32 KB(br)**，Vant 全量冗余被清除；
  - 首屏 CSS 压缩传输体积下降约 **32%**。

### B2 — 首屏仅预取底部 Tab 路由（消除 1MB+ 后台挤占）

- **文件**：`packages/mobile/src/utils/prefetch.ts`
- **问题**：原 `prefetchRoutes` 在浏览器空闲（`requestIdleCallback` / 回退 `setTimeout`）时**预取全部懒路由**，会把 `content` 路由的 md-editor 运行时（约 852 KB raw / 298 KB gz）与 `report` 路由的 echarts（约 365 KB raw / 124 KB gz）在**首屏刚进入时**一并拉取，占满移动端带宽与 CPU，用户感知「一直加载不完」。
- **改动**：仅预取 `meta.tab === true` 的路由（学习 / 任务 / 测验 / 我的）；刻意跳过 `content`（md-editor 重型）、`report`/`report/history`（echarts 重型）、`quiz/take`、`quiz/result`。这些重型路由仍保留按需懒加载，用户真正进入时才下载。
- **实测效果**：首屏空闲期后台下载量从 **~1.2 MB** 降至仅 4 个 Tab 路由的小 chunk（合计 < 60 KB），首屏「网络空闲 / 可交互」时间显著提前。

### B3 — 移除渲染阻塞的外部字体（首屏「长时间白屏」的真正根因）

- **文件**：`packages/mobile/index.html`、`packages/mobile/src/style.css`
- **问题**：`index.html` 中有一行 `<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Noto+Serif+SC...&display=swap">`。这是一个**渲染阻塞的外部样式表**——浏览器在拿到它之前不会渲染页面；而 `fonts.googleapis.com` 在**中国大陆网络环境下基本不可达**，请求会一直挂起直到 20~30s 超时，用户看到的就是「首次进入长时间白屏 / 加载转圈」。这正是 B1/B2 把体积压下去后**首屏仍慢**的隐藏根因——瓶颈根本不是体积，而是这一个外部阻塞请求。
- **改动**
  - 删除 `index.html` 中两条 `preconnect` 与那条 `fonts.googleapis.com` 的 `<link>`（保留注释说明原因，避免误加回）；
  - `style.css` 字体变量改为系统字体优先：`--ps-font-sans: -apple-system, BlinkMacSystemFont, 'PingFang SC', 'Microsoft YaHei', sans-serif;`、`--ps-font-serif: 'Songti SC', 'STSong', serif;`（去掉 Noto 依赖）。
- **安全**：无白屏风险——`style.css` 已带系统中文兜底字体栈，去掉 web 字体后中文优雅回退到 `PingFang SC` / `Microsoft YaHei`，样式与排版不受影响。
- **实测效果**：served `index.html` 经 curl 验证已无任何 `href="https://fonts..."` 真实链接，`index.html` TTFB ≈ 0.22s；首屏不再因外部字体请求卡白屏。

### B4 — mobile vendor 分包 + HTTP/2 并行（修复被屏蔽的配置）

- **文件**：`packages/mobile/vite.config.ts`、删除 `packages/mobile/vite.config.js`
- **问题**：项目里存在一个 2025-07-22 的**陈旧 `vite.config.js`**。Vite 加载优先级为 `.js` > `.ts`，因此我此前在 `vite.config.ts` 里做的 `manualChunks`、`target: esnext` 等所有改动**一直没生效**——每次构建都复现同一份把 vue+vant+axios 内联进单一入口 chunk 的产物，分包名存实亡。
- **改动**
  - 删除 `vite.config.js`，让 Vite 真正加载 `vite.config.ts`；
  - `manualChunks` 显式拆 `echarts` / `vant` / `vue`(含 vue-router/pinia/@vue) / `axios` 为独立具名 chunk，并**用 `vendor` 兜底会误吞 md-editor/highlight 等动态依赖**（曾因此把 852 KB md-editor 打进 2 MB 静态 vendor chunk、被 `modulepreload` 预载进首屏，造成回归），故**不写 `vendor` 兜底**——md-editor/highlight 保持动态 import 懒加载。
- **实测效果**
  - 首屏 `index.html` 仅 `modulepreload` `vue`(39 KB br) / `vant`(22.5 KB br) / `axios`(15.7 KB br) 三个 vendor chunk + 入口(3.1 KB br) + 2 份 CSS；
  - 852 KB 的 md-editor chunk 与 365 KB 的 echarts chunk **都不在首屏引用**，仍为进入对应路由才加载；
  - 三个 vendor chunk 均走 `Cache-Control: public, max-age=31536000, immutable`，**二次访问不再重复下载**（仅下入口 + CSS ≈ 38 KB br）。

### mobile 首屏关键路径对比（brotli 压缩传输体积）

| 阶段 | 首屏关键路径(br) | 二次访问(br) | 渲染阻塞成本 |
| --- | --- | --- | --- |
| 优化前（含 `fonts.googleapis.com` 外链 + vendor 内联） | ~131 KB | ~131 KB（入口含 vendor，hash 随依赖变） | **外部字体请求 20~30s 超时 → 长时间白屏** |
| B1/B2（去 Vant 全量 CSS + 只预取 Tab；此时 `.ts` 仍被 `.js` 屏蔽，vendor 内联） | ~95 KB | — | 外链仍在 → 仍白屏 |
| **B3/B4（去外链 + 启用 `.ts` vendor 分包）** | **~115 KB（7 文件 HTTP/2 并行）** | **~38 KB（vue/vant/axios immutable 缓存）** | **无（系统字体即时渲染）** |

- 首次进入字节数较 B1/B2 略增（vendor 拆 3 文件带来少量模块包装开销），但换来 **vendor 独立 `immutable` 缓存**（二次访问从 ~131/95 KB 降到 ~38 KB）与 **HTTP/2 并行下载**，且**根除了 20~30s 字体白屏**——后者才是「首次进入慢」的真正原因。
- 首屏后台预取量在 B2 已降至 < 60 KB（仅 Tab 路由），852 KB md-editor 与 365 KB echarts 仍按需懒加载。

## 四、验证结论

- A1 / A2 / A3 / B1 / B2 / B3 / B4 均已构建部署并验证生效。
- A3 验证曾因 **Node `fetch`(undici) 在 keep-alive 连接复用 + 未消费响应体时误读响应头** 产生假阴性；改用 **curl** 验证后四项缓存策略全部通过。经验：**验证「拦截器设置的响应头」必须用 curl 或严格消费 body 的客户端。**
- **B1 验证**：构建产物含 408 个 `.van-*` 类样式（grep 确认），首屏 `index-*.css` 经 brotli 直发 `Content-Encoding: br` + `immutable`，无白屏风险。
- **B2 验证**：`prefetchRoutes` 改为仅 `meta.tab` 路由；`content`(md-editor) 与 `report`(echarts) 仍按需懒加载，不再于首屏空闲期预取。
- **B3 验证（curl 真值）**：served `index.html` 已无任何 `href="https://fonts..."` 真实 `<link>`（仅保留解释性注释）；`index.html` 的 TTFB ≈ 0.22s，首屏不再因外部字体请求卡白屏。
- **B4 验证（curl 真值）**：删除陈旧 `vite.config.js` 后构建，`index.html` 仅 `modulepreload` `vue`/`vant`/`axios` 三个 vendor chunk；852 KB md-editor 与 365 KB echarts chunk 均不在首屏引用；vendor chunk 响应头 `Content-Encoding: br` + `Cache-Control: public, max-age=31536000, immutable`。
- **首屏实测（curl 真值，B3/B4 后）**：首次进入首屏关键路径 ~115 KB(br)，二次访问因 vendor 独立 `immutable` 缓存仅 ~38 KB(br)；prefetch 后台量 < 60 KB。
- 服务端运行于 3000，Redis 监听 6379 正常；重启后新 `index.html`（内存缓存）与磁盘新资产一致，无陈旧 404。

## 五、部署与回滚要点

- **部署顺序**：构建 admin / mobile → 运行 `precompress.cjs` 生成兄弟文件 → `nest.js build` 重编译 server → 重启。
- **注意**：Nest SPA fallback 将 `index.html` 读进内存，磁盘构建后必须重启服务。
- **缓存使失效**：白名单接口如需立即刷新，删除 Redis 键 `http-cache:{url}` 即可（TTL 到期也会自动失效）。
- **安全边界**：严格白名单，用户相关接口仅 `private`；新增白名单接口前必须确认其为「共享、非用户相关」只读接口。
- **踩坑：Vite 配置屏蔽**。Vite 加载配置时 `.js` 优先级高于 `.ts`。本项目曾长期存在一个陈旧的 `vite.config.js`，导致 `vite.config.ts` 的所有分包/目标改动失效而无人察觉。修改 Vite 配置后**务必确认实际生效的配置文件名**（删除多余副本、或用 `--config` 显式指定），并以「构建产物是否出现预期 chunk」为最终判据，而非仅看源码改动。

6. （已落地为 B4）mobile vendor 分包 + HTTP/2 并行 + `immutable` 独立缓存已完成；如需进一步，可评估把 `login`/`home` 之外的 Tab 路由也做更细的分子包。
